# 台灣標案投標文件生成(tw-tender-bid)

把一包招標資料變成可投出的投標文件。流程固定、每個關卡都要使用者確認,**不編造任何資格、實績、證照、人員、金額**。

## 鐵則(先讀)

1. **招標文件是唯一事實來源。** 優先序:法令與電子採購平台規定 > 最新公告、補充、更正、Q&A > 投標須知與官方表單 > 本 skill 的預設做法。衝突時以前者為準,並記錄出處。
2. **格式規格依招標文件,視覺風格才可自由變化。** 字體、字級、行距、紙張、邊界、標號、頁碼、頁數上限都是規格,逐案從須知抽取(`references/style-system.md`),產出後用審查腳本核對。風格(配色、標題樣式、封面版式)每案可不同。
3. **報價由人決定。** 你只提供報價結構、價格區間參考(公司 profile 的 `pricing_reference`)和試算;最終金額、總價、含稅與否必須由使用者確認。已送出的報價不可再改,要改一律另開新版。
4. **沒有證據就標【待補:項目;負責人】。** 不得用漂亮措辭蓋掉缺口,也不得把協力單位的實績寫成自己的實績。公司的已知限制見 profile 的 `known_limits`。
5. **官方表單優先。** 機關給的聲明書、切結書、標價單、授權書、封面、印模單,一律優先用原檔填寫;機關沒給範本才用 `scripts/bid_kit.py` 自建。
6. **數字只存一處。** 總價、單價、日期、專案名稱、公司全稱集中在 spec 檔,各章與附件都從那裡取,交件前跑 `audit_bid.py`。報價改版後,建議書內文仍留舊價是常見的錯。
7. **法規說法要查官方來源。** 引用法條只用 `references/tw-procurement-basics.md` 已查證的條文(附來源與日期);要引用別的條文,先查全國法規資料庫,不要憑記憶。
8. **保密。** 招標文件若標示機密、或須知有保密規定,先問使用者是否允許用 AI 處理再開始轉文字。過往案件的內容、金額、客戶名稱只引用做法,不帶進新案(`audit_bid.py` 會提醒殘留的舊案名)。不把招標文件或客戶資料上傳到不必要的外部服務。
9. **正式文件不使用 Emoji,繁體中文(台灣用語)。** 圖示只用單色幾何字元或純文字。成稿後可用環境中的台灣用語與去 AI 味 skill 檢查。
10. **簽名與印章不自動蓋。** 未經使用者逐份確認,產出一律是未蓋章版本。

## 公司 profile(換公司只換這個)

skill 本體不含任何公司資料。腳本依序讀取:

1. 環境變數 `TW_TENDER_PROFILE` 指向的 JSON
2. `~/.claude/tender-profiles/default.json`
3. `assets/company_profile.template.json`(全是【待補】;審查會提醒)

第一次使用先複製模板、填寫公司全稱、統編、負責人、地址、電話、信箱,以及:簽章圖檔路徑(只填路徑,不放進 skill)、公司公版素材路徑(人員配置、設備、甘特圖、經歷範本、合作同意書)、報價參考資料路徑、`brand_terms`(盲評檢查用的品牌字樣)、`past_case_keywords`(舊案關鍵字,抓複製貼上殘留)、`known_limits`(公司已知限制,例如缺少某類實績)。`python -I scripts/profile_loader.py` 可確認目前讀到哪一份。

## 流程(六個階段,四個人工關卡)

```
0 收件 -> 1 拆標(含格式規格) -> [關卡A] -> 2 策略、矩陣、風格 -> [關卡B] -> 3 撰寫 -> 4 審查 -> [關卡C] -> 5 組裝 -> [關卡D 送出前]
```

### 階段 0:收件與建檔

1. 確認招標資料齊全:公告、投標須知、評審(選)須知、需求說明書、契約草案、標價清單、各式表單、補充與更正、電子領標憑據。缺什麼就列出來問,不要硬做。
2. 建立工作資料夾 `{案名}_投標/`:`00_原始/`(原檔不動)、`01_拆標/`、`02_大綱/`、`03_草稿/`、`04_審查/`、`05_成品/`。
3. 轉文字:`python -I scripts/extract_rfp.py <招標資料夾> --out 01_拆標/text`。輸出 `_index.json` 記錄每個檔的方法與警告。出現 `needs_ocr`(掃描檔)或 `no_word_com`(.doc 無法轉)時,**明講哪些檔沒讀到**,請使用者提供可讀版本,不可說已完整解析。
4. 判斷案件類型:影像製作 / 活動執行 / 網站與資訊系統 / 一般勞務。類型決定章節重點(`references/chapter-blueprints.md`)。

### 階段 1:拆標

產出 `01_拆標/拆標報告.md`(欄位見 `references/rfp-analysis-template.md`),至少包含:

- 基本資料:案名、案號、機關、預算、履約期間、採購方式、依據法條。
- **資格標條件**逐條(含證明文件)與**不合格 / 廢標條款**逐條,每條附原文出處(檔名加頁或條號)。
- **評審項目、配分、合格分數、評定方式**、簡報時間與人數、是否盲評。
- 押標金、履約保證金、保固、付款條件、智慧財產權、保密與資安約定。
- 應繳文件清單(對照 `references/forms-checklist.md`)、份數、裝訂、封套標示、簽章與用印、遞送方式與截止時間。
- **格式規格**:另存 `01_拆標/format.json`(範本 `assets/format.template.json`),每項附原文出處;字號有歧義時寫入 `_notes`。
- 疑點與需向機關釋疑的問題(注意釋疑截止時間)。

### 關卡 A(必停)

拆標報告與 format.json 給使用者確認:是否投標、有無資格缺口、有無需釋疑項目、格式規格解讀是否正確。**未確認前不進入撰寫。** 實質不合格風險放最前面並附原文位置。

### 階段 2:策略、響應矩陣與風格

1. 建 `02_大綱/響應矩陣.md`,每個評審項目一列:

| 評審項目(原文) | 配分 | 評審重點 | 響應要點 | 證據(來源檔與頁) | 對應章節 | 缺口與補證 | 狀態 |
|---|---:|---|---|---|---|---|---|

   狀態只用:已證實 / 部分證實 / 待核驗 / 不適用。
2. **章節順序照評審項目排列**;配分高的項目篇幅較多(對照 `references/scoring-patterns.md`)。
3. 價格若納入評分,先確認占比與計算方式(`references/tw-procurement-basics.md`)。
4. 列出需要使用者提供的材料:實績、團隊簡歷、設備清單、協力單位同意書、證照。
5. **挑風格**(規格抽完之後):機關有識別色就先用;否則依案型提 3 個來自不同流派的方向,渲染預覽給使用者挑:
   `python -I scripts/preview_styles.py --out 03_草稿/style_preview --format 01_拆標/format.json --pdf`
   每案盡量不同,用 `--avoid` 排除最近用過的風格。可用 `scripts/make_style.py` 新增風格。詳見 `references/style-system.md`。

### 關卡 B(必停)

向使用者確認:亮點與方向、人員配置、協力單位分工、報價結構與金額、缺漏材料的取得方式、**選定的風格**。

### 階段 3:撰寫

1. 先寫成 spec(JSON),`scripts/build_proposal.py` 讀 spec 產生 Word。格式見 `references/spec-format.md`,範例 `assets/spec_example.json`。spec 帶 `"style"` 與 `"format"`;`format` 含 `numbering` 時章節標號自動依規定產生,不要手打。
2. 各章寫法見 `references/chapter-blueprints.md`;圖表(甘特圖、圓餅圖、長條圖)由 `build_proposal.py` 的 `chart` 區塊產生,字體跟隨規格。更細的版面直接 `import bid_kit`。
3. 公司既有素材(人員配置、設備、經歷、甘特圖公版)路徑記在 profile 的 `reusable_assets`;過往案件索引若有,記在 profile 的 `past_bids_index`。
4. 寫作規則:
   - 逐項回應評審項目與需求說明書條款,用招標文件的用語。
   - 量化:數量、人天、日期、單價。不寫「經驗豐富」「技術領先」這類空話。
   - 每個事實性陳述都要能指到證據;沒有就改成承諾性的做法描述,或標【待補】。
   - 須知允許載明廠商名稱才可寫公司名;盲評案不得出現公司名、Logo、人名(spec 設 `blind: true`)。

### 階段 4:審查

1. `python -I scripts/audit_bid.py 成品.docx --format 01_拆標/format.json --pdf 成品.pdf --price <最終總價> --project-name <案名> --items "<評審項目,逗號分隔>" [--blind] --out 04_審查/audit.json`
   檢查:殘留【待補】、Emoji、價格與缺漏、盲評洩漏、舊案字樣、專案與公司名稱、評審項目是否出現、簡體字與大陸用語,以及**格式規格**(紙張、邊界、中西文字體、字級、行距、頁碼、黑白、頁數)。
2. 對照 `references/audit-checklist.md` 逐項人工複核(資格、份數、簽章、封套、押標金、跨文件數字一致)。
3. 產出 `04_審查/審查報告.md`:blocking(必改)、warning(建議改)、通過項、需使用者決定。

### 關卡 C(必停)

審查報告給使用者,**所有 blocking 清零**才進組裝。

### 階段 5:組裝與送出前

1. 依 `references/forms-checklist.md` 補齊附件:優先填機關原檔;自建表單用 `bid_kit.py`。簽名與印章用公司既有去背檔,**逐份經使用者確認**後才用 `--seals` 產出蓋章版。
2. 合併成投標 PDF,產出 `05_成品/送件檢查表.md`:每個文件、份數、簽章、封套、押標金、遞送時間。
3. 轉出 PDF 後再核對一次頁數與字體(字型替換會讓版面位移)。

### 關卡 D(送出前)

使用者最後確認。你不代為上傳、寄送或投遞。

## 工具一覽

| 腳本 | 作用 |
|---|---|
| `scripts/extract_rfp.py` | 招標文件(docx、doc、odt、ods、pdf、xlsx)轉文字,標記掃描檔與讀不到的檔案 |
| `scripts/build_proposal.py` | spec JSON 轉服務建議書 Word(目錄、章標題、表格、圖表、元件、簽章區、自動標號);`--finalize` 用 Word 更新欄位 |
| `scripts/bid_kit.py` | 版面底層:風格包、規格覆寫、Word 標題樣式、表格、圖說自動編號、頁首章名、簽章區 |
| `scripts/bid_components.py` | 版面元件:重點數字卡、提示框、步驟、雙欄、章節扉頁、導言、封面幾何圖 |
| `scripts/preview_styles.py` | 同一份內容套多個風格並輸出預覽 PDF |
| `scripts/make_style.py` | 用色碼或 ui-ux-pro-max 配色資料產生新風格包 |
| `scripts/audit_bid.py` | 交件前自動審查,含格式規格核對 |
| `scripts/profile_loader.py` | 載入公司 profile |

## 已知限制

- 以台灣政府採購為前提,不處理中國大陸招投標(廢標、技術標與商務標等概念不能套用)。
- 不處理電子投標系統的實際上傳與加密;只備齊文件。
- 不提供法律意見。法律責任、資格疑義請洽機關窗口或法務。
- 引用的法條有查證日期,法規會修正;實際案件以該案招標文件載明的版本為準。
- 格式核對只能驗證 docx 本身(字體名稱、字級、行距、邊界等);PDF 內字型是否嵌入、不同電腦的字型替換,需人工在目標電腦確認。
- 圖樣用 A3 摺頁為 A4 的版面,需要在 Word 手動處理。
